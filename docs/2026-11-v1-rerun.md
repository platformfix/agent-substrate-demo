Re-running the demo on Substrate v1.0.1
=======================================

Run on 2026-11-20. The demo was moved from pre-1.0 commit `27bf3444`
(2026-09-18) to the v1.0.1 tag. Everything below was observed on one
machine on that date. Anything not measured is marked as such.

Short version: the parking scenario behaves the same on v1.0.1, a parked
request resolves with a 200 and the same saturation with parking off gets a
real 503. Getting there needed three script changes: a new installer, a new
way to reach actors, and a Docker plugin fix. The over-memory-limit probe
did not exercise the v1.0 fix, because this kernel lacks the feature that
fix depends on.

Versions and environment
------------------------

| | Baseline | Re-run |
|---|---|---|
| Substrate | `27bf34444e0c1a8762aebcafbc733a97c023cb4d` (pre-1.0, 2026-09-18) | `20778a6dbb01f13024642851bb592bf67c9fec05` (tag `v1.0.1`, 2026-11-20) |
| Demo scripts | `main` at `65aaa30` | this branch |

- Host: macOS on arm64, 10 CPUs, about 16 GB available to Docker.
- Docker 29.8.2 (client and server), running on OrbStack. The kernel is `7.2.12-orbstack-00394-gbecdd6130068`.
- kind v0.33.0, single-node cluster. Go 1.27.3 on the host. v1.0.1's `go.mod` asks for `toolchain go1.27.4`.
- No `/dev/kvm`, so both runs used the gVisor sandbox class only. The microVM path was not tested.

Both runs went through the same lifecycle CI uses: `./setup.sh`, then
`./preflight.sh`, then `DEMO_AUTO_RUN=1 DEMO_RUN_FAST=1 ./demo.sh`, then
`./reset.sh`, then `./cleanup.sh`.

Results side by side
--------------------

| Step | Pre-1.0 (`27bf3444`) | v1.0.1 |
|---|---|---|
| `setup.sh` | passed, 4m35s | 1st attempt failed after 2m12s (see below). Passed after the fix, 5m00s |
| `preflight.sh` | both PASS, 23.5s | both PASS, 58.1s |
| p3 parked, then served | `HTTP 200 in 2.638208s` | `HTTP 200 in 2.358194s` (second run: `2.555321s`) |
| p4 with parking off | `HTTP 503 in 0.027098s` | `HTTP 503 in 0.053867s` |
| p4 503 body | `actor ate-demo-parking/p4 unavailable: no free workers available` | `actor ate-demo-parking/p4 unavailable: no worker has room for the actor` |
| `reset.sh`, `cleanup.sh` | passed | passed |

The parked request's time is mostly the script's own `sleep 2` before it
suspends p1 to free a worker. It is not a latency benchmark, and the two
columns should not be read as one release being faster than the other.

The p3 and p4 numbers come from single runs. The pre-1.0 p4 figure came from
an extra `curl -w` I ran by hand after `demo.sh`, because `demo.sh` itself
runs that step with `curl -sf` and prints no status. The v1.0.1 p4 figure
came from the same kind of hand-run `curl -i` through `kubectl ate proxy`.

Load test on v1.0.1
-------------------

This is upstream's own `demos/parking/load.sh`: 30 seconds, four actors on
the two-worker pool, each looping request then suspend. I ran it on v1.0.1
only, since the pre-1.0 copy of the script reached actors a different way.

| | Parking off (`--parked-request-max=0`) | Parking on (default) |
|---|---|---|
| total requests | 312 | 232 |
| 200 OK | 153 | 232 |
| 503 | 159 | 0 |
| other | 0 | 0 |
| 200 latency | avg 0.201s, slowest 0.368s | avg 0.347s, slowest 2.853s |

With parking off, 159 of 312 requests (51%) were shed with a 503. With it
on, none were, and the cost showed up as latency: the slowest request waited
2.85s for a worker.

What broke, and what changed in the scripts
-------------------------------------------

1. **The installer script is gone.** `hack/install-ate-kind.sh` was deleted
   upstream (PR #3354). `setup.sh` now runs `go run ./cmd/ate-setup deploy
   ate-system` and `go run ./cmd/ate-setup deploy demo parking`, with
   `ATE_INSTALL_KIND=true` and `KUBECTL_CONTEXT=kind-agent-substrate-demo`.
   It installs with `--sandbox-classes=gvisor` and
   `--credential-provider='{"name":"k8s.io"}'`, which the install now requires.

2. **The router no longer accepts plain HTTP.** The pre-1.0 demo used
   `kubectl port-forward svc/atenet-router 8000:80` and set an
   `ate-target-actor` header on plain curl. On v1.0.1 the `atenet-router`
   Service exposes only 443 (HTTPS) and 8444 (TLS CONNECT), and a client has
   to present a Pod Identity certificate whose SPIFFE ID is on
   `--ingress-allowed-spiffe-ids`. Leave that flag unset and no client can
   reach any actor. `setup.sh` now passes
   `spiffe://cluster.local/ns/ate-system/sa/atenet-client`, and the scripts
   reach actors through `kubectl ate proxy actor pN 800N:80` (added in
   PR #3191), so p1 to p4 are on `localhost:8001` to `8004`.

   I predicted from the proxy's source that a saturated pool would show up
   as a dropped connection at curl. That prediction was wrong. The router
   accepts the CONNECT tunnel and Envoy answers inside it with a real
   `HTTP/1.1 503 Service Unavailable` (`server: envoy`), so the demo's
   "same saturation, real 503" beat survives unchanged.

3. **The first v1.0.1 setup failed on a Docker plugin.** It stopped at:

   ```
   [step]: setup_bundled_postgres
   unknown flag: --platform
   Error: while building the envoy-dataplane image: exit status 125
   ```

   v1.0 builds the `envoy-dataplane` image with `docker buildx`.
   `setup.sh` points Docker at an empty, isolated config directory, a
   workaround from the original build so `ko` never touches a gcloud
   credential helper. Docker looks for CLI plugins under `$DOCKER_CONFIG`, so
   the isolated directory hid this machine's `buildx` plugin, and `docker
   buildx build --platform=...` was parsed as plain `docker --platform`. I
   confirmed it directly: with an empty `DOCKER_CONFIG`, `docker buildx
   version` prints `docker: unknown command: docker buildx`. With
   `~/.docker/cli-plugins` symlinked in, it prints the buildx version.
   `setup.sh` now symlinks the plugins directory, and only that directory,
   into the isolated config.

4. **Smaller differences seen along the way.**
   - The WorkerPool API moved from `ate.dev/v1alpha1` to `ate.dev/v1`.
     ActorTemplates now require `resources.limits` (`cpuMillicores`,
     `memoryBytes`), and the parking demo sizes one actor per worker.
   - Every `kubectl ate` command now prints `Warning: no --token-file given;
     acting as the shared identity system:serviceaccount:ate-system:ate-client
     rather than as yourself.` This is harmless for the demo, but it shows on
     stage during `kubectl ate get actors`.
   - The counter workload no longer prints `hello from: <worker IP>`. On
     stage, the response no longer shows which worker served it. `kubectl
     ate get actors` still shows the worker pod.
   - `setup.sh` now refuses to run if `.vendor/substrate` is at a different
     commit from the pin. Before this, a leftover checkout would silently
     install the old version.
   - CI's Go version went from 1.27.0 to 1.27.4 to match the new
     `toolchain` line.

Over-memory-limit probe (v1.0 release note, PR #3106)
-----------------------------------------------------

The claim under test is "A gVisor actor going over its memory limit no
longer takes down every actor on its worker." `probes/memlimit/run.sh`
creates a one-worker pool with room for two actors, each capped at 256Mi,
running a small `memhog` server. It asks actor m1 to allocate 400 MiB while
polling its neighbour m2 once a second.

Observed on v1.0.1. This is abridged: columns are trimmed to `...`, eight of the ten m2 polls are left out, and each poll's `(HTTP 200)` is joined onto its line. The full output is what `run.sh` prints.

```
ate-probe-memlimit   m1   ...   ACTOR_STATE_RUNNING   ate-probe-memlimit/memlimit-7b444bb8c9-dpfzn
ate-probe-memlimit   m2   ...   ACTOR_STATE_RUNNING   ate-probe-memlimit/memlimit-7b444bb8c9-dpfzn
memlimit-7b444bb8c9-dpfzn   1/1     Running   0          55s
==> m1: allocate 400MiB against a 256Mi limit
upstream connect error or disconnect/reset before headers. reset reason: connection termination
-> m1 HTTP 503 in 0.482385s
==> m2 (the neighbour), once a second for 10s
[+0s] alive, holding 0 MiB (HTTP 200)
...
[+10s] alive, holding 0 MiB (HTTP 200)
ate-probe-memlimit   m1   ...   ACTOR_STATE_CRASHED   <none>
ate-probe-memlimit   m2   ...   ACTOR_STATE_RUNNING   ate-probe-memlimit/memlimit-7b444bb8c9-dpfzn
    message: gVisor sandbox exited
memlimit-7b444bb8c9-dpfzn   1/1     Running   0          67s
```

The neighbour answered all ten polls with a 200, and the worker pod did not
restart. **This is not evidence that the v1.0 fix works**, and it should not
be quoted that way. Three things show that the fix never ran here:

- At startup the worker logged: `Kernel has no cgroup memory pressure (PSI),
  so sandboxes keep memory.max and an OOM kill in one can restart the
  worker`. The new guard is enabled only when `memory.pressure` exists
  (`ateworkerService.throttleMemory = cgroup.PSIEnabled(...)` in
  `cmd/ateworker-gvisor/main.go`), and this kernel has no
  `/proc/pressure/memory`.
- The guard reports its kills as "killed for exceeding its memory limit".
  m1's crash message was the generic "gVisor sandbox exited".
- The PR describes the original bug as happening "on some nodes", depending
  on the node's systemd and runc. It may never have reproduced on this
  OrbStack kernel. I did not run the probe on the pre-1.0 pin: that version's
  template has no `resources` field, so the same probe would not have been
  comparable.

What I can say: on this kind setup, one actor blowing its memory limit
killed only that actor, and its neighbour on the same worker kept serving.
That happened through the kernel's ordinary per-sandbox `memory.max`, not
the v1.0 guard. Testing the actual fix needs a node with PSI enabled (the PR
author tested on GKE 1.37.1). That was out of scope for this run.

Not tested: the microVM fix (PR #3429), because there was no `/dev/kvm`.
Also not tested: "Suspending actors no longer OOM-kills tight worker pods"
(PR #3353). The load test suspended actors hundreds of times, but I did not
check the parking workers' restart counts afterwards, and nothing about that
pool's sizing was "tight", so it says nothing about the claim either way.

Reproducing
-----------

```bash
./setup.sh
./preflight.sh
DEMO_AUTO_RUN=1 DEMO_RUN_FAST=1 ./demo.sh
./reset.sh
./.vendor/substrate/demos/parking/load.sh   # parking on; patch --parked-request-max=0 for off
./probes/memlimit/run.sh                    # optional, needs the cluster from setup.sh
./cleanup.sh
```
